Headers present on every response (no need to burn requests to read them):
  x-ratelimit-limit-requests  (always RPD)
  x-ratelimit-limit-tokens    (always TPM)
  x-ratelimit-remaining-requests (RPD)
  x-ratelimit-remaining-tokens   (TPM)
  x-ratelimit-reset-requests     (RPD reset, e.g. "2m59.56s")
  x-ratelimit-reset-tokens       (TPM reset, e.g. "7.66s")
  retry-after: only present on 429.

Per-request token overhead:
- A trivial "Reply with exactly: OK" request (max_tokens=5) costs ~78 tokens:
  73 prompt + 5 completion. Prompt overhead is large relative to the answer.
- Consequence: at ~78 tokens/request, TPM allows ~100 tiny req/min but RPM
  caps at 30. For paper-sized prompts (~1000-3000 tokens) TPM binds first,
  likely limiting to ~2-8 req/min. TPM is the real choke point, not RPM.
- Groq reports usage breakdown per request: queue_time, prompt_time,
  completion_time, total_time. Useful for "where the time goes".

What the real run taught us (each was a bug or a limit found by running):
1. TPM = 8000 CONFIRMED by a real 429: "Limit 8000, Used 7556" on tokens per
   minute. Confidence now high. RPM was already confirmed at 30.
2. Verifier was broken for reasoning models: max_tokens=60 produced EMPTY
   content (all tokens spent on hidden reasoning), so every answer looked
   unverified. At 250 tokens it returns "YES" / "NO: reason". Fixed with
   PipelineConfig.verify_max_tokens.
3. Model self-refusal was mis-handled: the model answered exactly
   "NOT_IN_PASSAGES" for France/quantum, but the pipeline treated it as a bad
   draft and retried, ending "unverified" (graded wrong). Now NOT_IN_PASSAGES
   maps to status=refused with the standard refusal text, in one call (~1.2k
   tokens instead of ~2.7k).
4. Grading bug: "4,000 warmup steps" failed the "4000" fact check. Grader now
   normalises NFKC and thousands separators. Rerun: correct.
5. Retrieval miss: "h = 8 parallel attention layers" sits at rank 4 for the
   heads question; k=3 missed it and the model honestly refused. k=4 fixes it.
6. Failed requests (429) are not quality failures: grade is empty and excluded
   from denominators (19 graded of 20).

Remaining wrongs (2): t-self-attention and m-inner-monologue, both status
unverified. Their drafts were not logged on that run (proto before
raw/answers.jsonl), so the exact cause is unknown. Next run will log answers.

ROOT CAUSE FOUND AND FIXED (the big one)
----------------------------------------
The remaining "unverified" answers were not retrieval problems: the drafts and
verdicts were EMPTY because gpt-oss-20b is a reasoning model and hidden
reasoning consumed the whole max_tokens budget (tokens_out hit the cap with no
content). Fix:
  - GroqClient sends reasoning_effort="low"
  - draft max_tokens 400 -> 700, verify 250 -> 400
  - Answer.verification records the verdict, and raw/answers.jsonl keeps the
    full draft text for auditing.
Rerun of the 3 affected questions (t-self-attention, m-inner-monologue,
m-codec): all correct. Quality after fix: 80% correct, 20% refused correctly,
0% wrong, 0 failures, 3392 tokens/answer, TTFT p50 486 / p95 740 ms.
This is the single most consequential engineering lesson of the build: for
reasoning models, token budgets must cover thinking, not just output.

REPORT CONVENTIONS (relay/report.py)
------------------------------------
- latency percentiles use only status=ok rows, nearest-rank
- peak queue = max overlapping [start_time, start_time+total_ms] intervals
- duration = last start - first start + that request's total_ms
- timed out / given up = timeout + error (rate_limited is separate)
- cost = 0 on free tier; --price-in/--price-out for paid math

RETRIEVAL OBSERVATIONS ON THE REAL CORPUS (zero-cost run, 2026-11-09)
-----------------------------------------------------------------------
How this library misleads a naive retriever - three concrete examples:

1. Appendix transcripts and figure captions flood the ranking.
   Q: "How many attention heads does the Transformer use?"
   Top hits include the attention-visualization appendix (p.13: "...a majority
   of americans...") and a Moshi appendix page, ahead of the actual Table 3
   discussion (p.9). A naive top-k retriever would draft from junk.

2. BM25 scores are not comparable across queries, so a fixed refusal floor
   lets nonsense through.
   Q: "What is the capital of France?" (answerable by no paper)
   Top hit scores 11.08 - higher than several genuinely relevant hits for
   real questions - because the Moshi appendix contains chat transcripts
   ("user: hello, i wanted to talk..."). Our is_answerable() gate would say
   "answerable". Grep for the word usage is not evidence of an answer.

3. Tables and numbers get split by character chunking.
   The exact answer ("h = 8 heads", d_model = 512) lives in a table whose
   rows are separated by layout; 1200-char pieces straddle the header and
   the row, so the number can fall outside the retrieved piece even when the
   caption is retrieved. Question answering needs the table vicinity kept
   together (motivates overlap and/or page-level re-expansion).
